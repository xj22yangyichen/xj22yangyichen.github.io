## 项目概述

STLite 是我在上海交通大学 CS1951 数据结构课程中的容器实现项目。它按照给定接口实现了 `vector`、`map`、`priority_queue`、`deque` 和 `list`，并提供相应测试数据。

使用容器时，通常只关心插入、删除和访问的结果；实现容器时，还必须处理对象何时构造、何时析构、迭代器指向哪里，以及操作失败后原有状态是否仍然有效。STLite 把这些平时隐藏在库内部的问题放到了实现的中心。

## 五种容器，五种组织方式

| 容器           | 当前实现中的结构                   | 主要关注点                   |
| -------------- | ---------------------------------- | ---------------------------- |
| vector         | 连续内存与起点、终点、容量边界指针 | 扩容、元素搬移与生命周期     |
| map            | 红黑树                             | 有序查找、旋转与插入删除修复 |
| priority_queue | 二项堆                             | 堆的合并与比较器异常处理     |
| deque          | 块指针表与分段存储                 | 跨块随机访问、首尾操作       |
| list           | 双向链表                           | 节点链接与迭代器遍历         |

这些结构共享相似的使用接口，但不应该共享相同的性能预期。例如，连续数组适合随机访问，中间插入则需要移动元素；链表修改链接比较直接，却不能通过下标直接定位任意节点。实现容器的过程，也是在把接口对应到具体的数据结构约束。

## vector 与 deque：内存和对象要分开管理

模板参数 `T` 不一定有默认构造函数。为了给容量预留空间而直接构造一整段对象，会给容器施加不必要的类型要求。当前实现通过原始内存分配、placement new 和显式析构，把“拥有存储空间”和“其中存在有效对象”分开。

`vector` 用三个指针分别描述已分配空间的起点、有效元素的结尾和容量的结尾。扩容或插入时，不仅要安排数据位置，还要确保构造与析构对应，避免把尚未构造的空间当成有效元素访问。

`deque` 则使用分段存储。当前代码将块大小设为 64，通过块指针表定位各段。迭代器同时保存当前元素、块边界和块指针的位置；跨块移动时，需要把偏移量换算为块的位移与块内位置。负方向移动尤其容易出现边界错误，不能简单套用正数除法。

## map：让树的结构对迭代器保持可解释

`map` 的节点保存父节点、左右孩子、键值对和颜色。插入与删除需要维护红黑树约束，旋转则改变局部连接关系而保留键的中序次序。

与此同时，容器还要支持顺序遍历。迭代器的递增和递减依赖孩子与父节点关系，边界位置则需要和容器的头节点设计一致。因此，树的平衡修复与迭代器行为不能分开考虑：局部修改完成后，父子关系和边界仍然必须可用。复制容器也需要复制整棵树，而不是让两个容器共享同一批可变节点。

## priority_queue：合并与异常后的状态

优先队列使用二项堆组织节点，每个节点保存度数以及父、孩子和兄弟指针。合并时先组织根链，再连接相同度数的树。相比只提供入队和出队的接口，这个项目还实现了两个队列之间的 `merge`。

比较器可能抛出异常，所以修改指针之前需要考虑操作能否撤回。当前实现设计了 `NodeBackup` 和 `RollbackLog`，保存被修改节点的连接与度数信息，在异常路径上恢复。

这份机制围绕比较器异常组织回滚：修改节点前记录连接关系，异常发生后按逆序恢复，将结构维护与异常处理纳入同一条操作路径。

## 测试与项目价值

容器的验证关注空容器、首尾操作、复制后的独立修改、无默认构造的元素类型，以及比较器抛出异常后的状态。这些场景将接口语义、内存生命周期与数据结构不变量联系起来。

这个项目的价值在于把抽象接口落实为可以逐项检查的不变量：内存属于谁，有哪些对象已经构造，树或链的连接是否有效，迭代器是否仍符合接口约定。这些问题也会直接影响后续系统项目中自制容器的可靠性。
