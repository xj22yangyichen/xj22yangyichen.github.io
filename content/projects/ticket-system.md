## 项目概述

Ticket System 是一个使用 C++ 实现的命令行火车票管理系统，也是我在上海交通大学 CS1951 数据结构课程中完成的项目。系统围绕查票、买票和退票组织功能，并提供用户账户、车次和订单管理。

用户可以按出发站、到达站和日期查询直达或一次换乘方案，查看行程时间、票价与余票，再选择购票。余票不足时可以提交候补订单；退票释放座位后，系统会检查候补队列，为满足条件的订单补票。用户还可以查询自己的历史订单及其状态。

车次管理功能负责维护线路、停靠站、运行时刻、票价和发售日期。底层使用自制 B+ 树将用户、车次、余票和订单等数据保存在文件中，并通过缓存减少重复读取。业务流程与存储结构共同构成这套系统的实现。

## 用 B+ 树连接业务和外存

系统使用自制 B+ 树保存主要业务数据，并通过不同键组织访问路径。完整记录和辅助索引共同服务于查询：

| 数据     | 索引键             | 用途                         |
| -------- | ------------------ | ---------------------------- |
| 车次     | 车次编号           | 读取线路、时刻和票价         |
| 停靠站   | 站名               | 找到车次及该站在线路中的位置 |
| 余票     | 车次编号、始发日期 | 保存一次运行中各区间的座位数 |
| 订单     | 时间戳             | 定位订单记录                 |
| 用户订单 | 用户名             | 获取用户对应的订单时间戳     |
| 候补队列 | 车次编号、始发日期 | 查找该次运行的候补订单       |

B+ 树模块维护节点缓存，业务层还缓存车次和车站查询结果，减少重复读取。两类缓存的粒度不同：一个面向存储节点，一个面向业务对象。更新记录时，需要同时关注文件中的数据与内存中已经读出的状态。

## 区间余票与运行日期

对于一条经过 A、B、C、D 的线路，座位按 A—B、B—C、C—D 三段保存。购买 A 到 C 的车票，需要同时占用前两段；这张车票的可售数量由两段剩余座位的最小值决定。购买成功后逐段扣减，退票时再逐段加回。

日期也不能只取用户输入的乘车日期。列车从始发站出发后，可能经过午夜才到达用户的上车站。因此，系统需要将上车日期换算为这趟列车的始发日期，再定位正确的余票记录。代码通过分钟偏移和日期换算处理跨日运行，使时刻表与座位库存使用同一个运行实例。

## 直达与一次换乘查询

直达查询先利用车站索引筛选候选车次，再判断起终点顺序和发售日期，计算出发到达时间、区间价格和余票。结果可以按总行程时间或价格排序，并进一步处理相同条件下的车次顺序。

一次换乘查询需要组合两趟列车。除了确定共同换乘站，还要找到第二程实际可衔接的发车日期：第二程的时刻即使比到站时刻早，也可能在次日形成合法衔接，但必须仍处于发售日期范围内。

这个过程的关键是使用完整的日期与时间进行比较。只比较一天内的时刻，会漏掉跨日方案，也可能把已经错过的列车误判为可乘。系统围绕一次换乘业务，将车站匹配、跨日衔接和方案排序整合到完整的查询流程中。

## 候补与退票形成状态转换

订单具有 `SUCCESS`、`PENDING` 和 `REFUNDED` 三种状态。有余票时，购票直接扣减库存并生成成功订单；余票不足且用户接受候补时，订单进入候补状态，并加入对应车次与始发日期的候补索引。

成功订单退票后，系统恢复相关区间的座位，再遍历这趟车的候补订单。每笔候补都要重新检查自己覆盖的区间，满足数量要求后才扣减座位并转为成功。不满足条件的订单保留在队列中，后面的订单仍可能因为区间不同而获得满足。

候补订单本身退票，则从候补索引中移除并标记为已退票，不应释放它从未占用的座位。区分这两条路径，是维持库存与订单一致性的关键。
